Built on NVIDIA Nemotron

Safety comes from the architecture.
Judgement comes from Nemotron. Pick the right size for each job, and run it where the data lives.

Every AI in RecoveryPact is a Nemotron model, seven in all: the two negotiating guardians, the auditor, the guard that screens what they read, the embeddings behind their memory, and a 4B model that runs the whole pact on our own hardware. And Nemotron's provenance decides what runs: the authority touches the database only when a signed Nightshift receipt names the Nemotron model that proposed the action. We benchmarked the same eight incidents across the Nemotron family, with and without our reasoning scaffold, and with a mixed-size team.

Why a DGX Spark

Incident data should not leave the building

A recovery agent reads exactly what companies guard most: which sessions touch payments, which customers are failing, whether the financial close is running. With open Nemotron weights the whole pact can run on-premises: every model in the role cards above fits on one DGX Spark together, next to the database, so untrusted production text is screened and reasoned over without leaving the building.

Privacy is already proven on our own hardware. Speed is the gap.

Where the time goes today, measured. Every guardian turn is a round-trip to a hosted model. Direct to the NVIDIA API, the median incident takes 78 s with Ultra and 52 s with Super. Through cloud routing it takes 239 s, about 45 s per call. Super's only misses in our benchmark were hosted-API errors. Speed is the pact's one weakness, and it is network time and hosted-provider failures, both of which a DGX Spark next to the database removes.

One piece already runs off the cloud, measured. We served Content Safety 4B ourselves (Q4_K_M, llama.cpp) on a laptop and re-ran the guard benchmark. The three-layer guard scored the same as with the hosted model: 14/15 on the tuning set and 4/10 on the held-out set (hosted: 3/10), 0 false positives in both. The cost was speed: 3.9 s per string on a 4 GB GTX 1050 and about 27 s on the laptop CPU, where reasoning mode could not finish inside our 90 s timeout. Then we served it through Nightshift's own local lane: 100 guard calls, every one signed by Nightshift as answered on this machine (kind: local, privacy: local-only). The policy model does not need the cloud; it needs a Spark. (tuning, held-out)

Then the whole pact, with the cloud taken out. Both guardians and the auditor answered as Nemotron 3 Nano 4B on the same laptop's CPU, through Nightshift's local lane, with no NVIDIA key in the stack. The authority required every guardian answer to be signed by that on-machine model. All 12 answers came back signed local-only, the prompt went nowhere, and every signature verifies. It failed safe, not well: in incidents A and B the 4B model on a laptop CPU could not settle the trade-off and handed both to a human (0 of 2 right, 0 unsafe), at about 17 minutes per answer. Every call.

The Spark deployment is written. compose.spark.yaml serves all five models above on one Spark with vLLM, at the memory split in the table, and points every AI in the pact at them, with the NVIDIA key a placeholder so nothing can reach a hosted API. One command: docker compose -f compose.yaml -f compose.spark.yaml up -d.

So the private, signed, fully local loop already works. What a laptop lacks is model size and speed, which is what a Spark adds: Super VL, which scored 22/24 hosted, fits on one at FP4. We have not run it on a Spark: the headline results ran on hosted Nemotron, and the Spark file is the next step, not a Spark benchmark.
