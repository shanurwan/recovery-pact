Why a DGX Spark

Incident data should not leave the building

A recovery agent reads exactly what companies guard most: which sessions touch payments, which customers are failing, whether the financial close is running. With open Nemotron weights the whole pact can run on-premises: every model in the role cards above fits on one DGX Spark together, next to the database, so untrusted production text is screened and reasoned over without leaving the building.

Where the time goes today, measured. Every guardian turn is a round-trip to a hosted model. Direct to the NVIDIA API, the median incident takes 78 s with Ultra and 52 s with Super. Through cloud routing it takes 239 s, about 45 s per call. Super's only misses in our benchmark were hosted-API errors. Speed is the pact's one weakness, and it is network time and hosted-provider failures, both of which a DGX Spark next to the database removes.

One piece already runs off the cloud, measured. We served Content Safety 4B ourselves (Q4_K_M, llama.cpp) on a laptop and re-ran the guard benchmark. The three-layer guard scored the same as with the hosted model: 14/15 on the tuning set and 4/10 on the held-out set (hosted: 3/10), 0 false positives in both. The cost was speed: 3.9 s per string on a 4 GB GTX 1050 and about 27 s on the laptop CPU, where reasoning mode could not finish inside our 90 s timeout. Then we served it through Nightshift's own local lane: 100 guard calls, every one signed by Nightshift as answered on this machine (kind: local, privacy: local-only). The policy model does not need the cloud; it needs a Spark. (tuning, held-out)

The guardians ran on hosted Nemotron (the NVIDIA API directly and through Meterless Nightshift). Running them on a DGX Spark is the next step; the numbers above are what it would remove, not a Spark benchmark.
